PixelRAG: Retrieval Over Pixels, Not Text

Created on June 21, 2026

2026   ·   paper-notes   rag   computer-vision   retrieval   multimodal   ·   technical

Notes on PixelRAG (StarTrail / Berkeley SkyLab, BAIR, Berkeley NLP) — a retrieval-augmented generation system that does something deceptively simple: instead of parsing documents into text, it renders them as screenshots and retrieves over the images directly.

Motivation: text parsing throws away the document

Classic RAG pipelines run every web page or PDF through a text extractor, chunk the output, embed the chunks, and retrieve. That works well for prose, but it quietly destroys everything that isn’t prose. A financial table becomes a flattened stream of numbers with no row/column structure. A chart becomes nothing at all. A multi-column layout, a figure caption tied to a diagram, a form — all collapse into ambiguous or missing text.

The PixelRAG framing is blunt: traditional RAG “parses the page to text chunks and loses the table — the reader can’t find the answer.” When the answer lives in visual structure, the retrieval step has already failed before the reader model ever sees it.

The bet PixelRAG makes is that modern vision-language models are now good enough to read a screenshot the way a person does. So why throw the pixels away? Keep the page as an image, embed the image, retrieve the image, and hand the image to a VLM reader. The visual structure survives end to end.

Approach: a modular pixel-native pipeline

PixelRAG is built as a set of independent, composable CLI stages rather than one monolith:

  • pixelshot (render) — converts documents to screenshot tiles. Web pages go through headless Chromium over the Chrome DevTools Protocol (CDP); PDFs render via poppler.
  • pixelrag chunk — organizes tiles and extracts metadata.
  • pixelrag embed — embeds each tile into a vector using a fine-tuned vision-language embedding model.
  • pixelrag build-index — builds a FAISS index over the tile vectors.
  • pixelrag serve — a FastAPI service that embeds a query and returns the nearest tiles.

The clean stage boundaries matter: rendering is a throughput-bound systems problem, embedding/indexing is a GPU problem, and serving is a latency problem. Decoupling them lets each be scaled and optimized on its own.

The embedding model

Retrieval runs on Qwen3-VL-Embedding-2B, a vision-language embedding model producing 2048-dimensional vectors, fine-tuned with LoRA adapters on screenshot data. The training recipe is the interesting part:

  • LLM-augmented query generation — synthetic queries are generated against rendered tiles to create training pairs.
  • Filtering — low-quality or ambiguous pairs are dropped.
  • Hard-negative mining, staged — training progresses from in-batch negatives → “naive” hard negatives → dynamic hard negatives with the ViT unfrozen. Dynamically re-mining hard negatives as the model improves keeps pushing the decision boundary, and unfreezing the vision tower late lets the image encoder itself specialize to screenshot content rather than natural photos.

Both a base (off-the-shelf) and a LoRA-fine-tuned index are maintained, which makes it easy to ablate exactly how much the screenshot-specific fine-tuning buys you.

Indexing and retrieval

Vectors land in a FAISS IVF index (inverted-file approximate nearest neighbor) for fast search over tens of millions of embeddings. A query is embedded into the same space and the top-k tiles (k=3 by default; k=1,2,5 in ablations) are retrieved. Because the index is image-native, the system can also stand up a parallel text index over the same corpus — which is precisely what lets the authors compare pixel-space vs. text-space retrieval head-to-head on the same documents.

Scale: Wikipedia as a pixel corpus

PixelRAG ships a pre-built index over all of English Wikipedia — roughly 7.1M articles rendered into ~30M tiles (~5.6–8.5 TB of images), served from a hosted API (api.pixelrag.ai) so you can query it with no local setup or GPU. The fine-tuned FAISS IVF index alone is on the order of 200 GB over ~26M vectors. A 199 MB URL-to-tile metadata map coordinates retrieval back to source articles.

Technical nuances worth calling out

Rendering is the real bottleneck — and it got serious engineering. Turning 7M articles into 30M screenshots is a systems problem, and the throughput work is genuinely the most novel engineering in the repo. Highlights:

  • Tiles are rendered as tall strips (≈875×8192 px), JPEG quality 50, ~305 KB each — a layout that captures a long vertical span of a page per tile.
  • 48 Chrome workers on a single AMD EPYC box pull articles from a local kiwix-serve Wikipedia mirror. The pipeline per tile: navigate → wait for fonts.ready + image-load → requestAnimationFrame → CDP screenshot → disk.
  • The screenshot capture stage dominates (≈321 ms/op at 48 workers), and at high concurrency IPC/OS scheduling overhead (240 threads on 128 cores) is ~56% of capture time — not navigation, not compression.
  • Key wins came from going direct to the CDP websocket (bypassing Playwright’s IPC), event-driven waits instead of fixed sleeps, and custom Chromium patches that write raw BGRA into shared memory so Chrome’s own thread pool can JPEG-encode asynchronously. A work-stealing queue and a phased-semaphore strategy balanced load. Net result: 20 → 109 tiles/sec, a 5.5× speedup.
  • The instructive failures: --single-process hit 168 t/s but 74% correctness loss (broken rendering), --in-process-gpu was faster but cost ~10% correctness, and farming JPEG encoding to a ProcessPoolExecutor slowed things down (40 t/s) because cross-process IPC dwarfed the win. The recurring lesson: pixel-perfect fidelity and raw speed trade off directly, and the fastest options quietly corrupt the very signal the whole system depends on.

The evaluation is modality-aware. Because the same corpus exists as both pixels and text, PixelRAG benchmarks where visual retrieval actually helps. The suite spans SimpleQA, Natural Questions, NQ-Tables, MMSearch, EVQA, MoNaCo (multi-hop), and LiveVQA, graded with GPT-4.1 judges and F1/alias matching, with a Qwen3.5-4B-class VLM as the reader. NQ-Tables and the VQA-style tasks are exactly where text parsing should lose the most information — and thus where pixel retrieval should pay off.

It’s designed to be used by agents. The repo includes a Claude Code “pixelbrowse” skill that lets an assistant screenshot and analyze pages on the fly, and the hosted Wikipedia API means a model can do visual retrieval without any infrastructure. PixelRAG is positioned not just as a research artifact but as a retrieval backend.

Takeaway

PixelRAG’s core thesis is that the lossy step in RAG isn’t retrieval or generation — it’s the text extraction at ingestion. By keeping documents as pixels all the way through embedding and retrieval, it preserves the tables, charts, and layout that VLMs can now read directly. The research contribution is the screenshot-tuned embedding model and the modality-controlled evaluation; the engineering contribution, equally substantial, is making “render the entire web at scale” actually tractable.
